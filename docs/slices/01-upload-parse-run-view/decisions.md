# Slice 1 decisions: upload, parse, run view

Settled in a grilling session before implementation. Scope comes from the slice 0 handoff.

## API
- `POST /runs`: multipart with a `cv` file part and a `jobDescription` text part (the Job Description is text, not a file). Success: `201`, body `{ id }`, `Location: /runs/:id`. Rejection: `4xx { code, message }` and no Run is created, so `failed` in `RunView` only means a later failure.
- `GET /runs/:id`: a `RunView` validated against `RunViewSchema`. A malformed, unknown or expired ID returns `404 { code: "RUN_NOT_FOUND" }`. Expiry is checked on read, so the slice 5 sweep is cleanup, not what enforces privacy. `RUN_NOT_FOUND` is an API error, not a `RunErrorCode`.
- The Run ID comes from `crypto.randomUUID()`.

## Parsing
- Parsing is synchronous inside `POST /runs`. Libraries: `unpdf` (PDF), `mammoth` (DOCX), `multer` with memory storage. The upload is never written to disk.
- File type is detected by magic bytes (`%PDF-`; ZIP containing `word/document.xml`), not by MIME type or extension. Anything else is `UNSUPPORTED_FILE`.
- Limits (all in config): CV 5 MB, PDF 5 pages, DOCX 30,000 characters, Job Description 20,000 characters. A PDF averaging under about 100 characters per page is `SCANNED_PDF`.
- Corrupt or encrypted files, and extraction taking over about 10 seconds, are `EXTRACTION_FAILED`.
- `JOB_DESCRIPTION_TOO_LONG` is added to `RunErrorCodeSchema`.
- For untrusted PDFs, check the page count before extracting text and set `maxImageSize` (unpdf's README puts resource limits on the caller).

## Storage
- Prisma, with the `runs` table in the `app` schema; see ADR 0005.
- `runs` holds id, status, timestamps, expiry, export path, and the transitional `cv_text` and `jd_text` columns; see the addendum in ADR 0003.
- A successful Run is stored as `extracting`: `parse` done, the other six steps pending, `job` null, `expiresAt` = `createdAt` + `RUN_TTL_DAYS`. Nothing advances it until slice 2.
- A thin `RunStore` module (`create`, `get`, `delete`) hides Prisma. `config.ts` validates env with Zod and fails fast.

## Testing
- Vitest. Unit tests for the parsers; `supertest` integration tests against a real `resume_ai_test` Postgres (no DB mocking, so migrations are exercised).
- Fixtures are synthetic (a fictional CV), generated by a script in `backend/test/fixtures/` and committed. The Postman collection in `postman/` reuses them. No real CVs in the repo.

## Structure (changed after the first implementation)
The first version kept routes, handlers and rules in `app.ts`. They are now separated under `backend/src/runs/` as router, controller and service, with the store beside them, and `app.ts` only wires them. Imports use the `@/` alias. Both rules are in the root `CLAUDE.md`.
